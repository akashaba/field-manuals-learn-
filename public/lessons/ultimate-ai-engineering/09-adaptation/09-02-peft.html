09.02 — PEFT (Parameter-Efficient Fine-Tuning)

**Module 9: Adaptation** · Subtopic 2 of 4

Prerequisites: 09.01 (SFT objective, memory math), 01.01 (attention and MLP blocks), 08.03 (multi-LoRA serving). Outcome: you can explain the PEFT method families mathematically and count their trainable parameters in closed form. You can pick a method from the constraints (quality, memory, serving engine, number of tenants), and operate a fleet of adapters: training, versioning, merging, and multi-adapter serving.

Status check (September 2026).

  • Hugging Face PEFT 0.21 implements 40+ methods. These include LoRA and its variants (DoRA, PiSSA, OLoRA, CorDA, rsLoRA, VeRA, AdaLoRA, LoHa/LoKr, RandLoRA, …), orthogonal fine-tuning (OFT/BOFT/HRA), (IA)³, prompt/prefix/P-tuning, and newer entries such as HiRA, GLoRA, BEFT and Uni-LoRA.
  • In production, "PEFT" mostly means LoRA. It is the one family that merges into the weights with zero inference overhead, and the one that serving engines support natively (vLLM multi-LoRA, S-LoRA/Punica-style kernels). Everything else is a research option to benchmark, not a default.

# 1. Why Parameter-Efficient

Full fine-tuning (09.01 §3) costs 16 bytes/parameter of optimizer state and produces a full copy of the model per task. PEFT freezes the base $W_0$ and trains a small set of parameters $\phi$, with $|\phi| \ll |W_0|$:

$$ h = f\big(x;, W_0,, \phi\big),\qquad \nabla_{W_0} \text{ not stored},\qquad \text{optimizer state} \propto |\phi|. $$

What this buys in production:

Benefit Mechanism Legislative example
Memory Gradients and Adam state only for $\phi$; the frozen base can be quantized (QLoRA, 09.03) Fine-tune an 8B model on one 24 GB GPU
Storage and deployment One base plus many adapters of 1–300 MiB Per-task adapters: summaries, fiscal notes, amendment explanations, committee minutes
Multi-tenant serving Swap or batch adapters over one resident base One vLLM deployment serving all departments' adapters
Less forgetting Constrained update capacity; the base is untouched General capability preserved for out-of-domain requests
Fast iteration and rollback Retrain or roll back an adapter without touching the base Adapter version pinned in the bundle (08.05 §2)

# 2. The Method Families

                      ┌─ ADDITIVE ──── new modules or inputs:  bottleneck adapters (Houlsby, Pfeiffer), (IA)³ scaling vectors,
                      │                                       soft prompts: prompt tuning, prefix tuning, P-tuning v2
 PEFT ────────────────┼─ SELECTIVE ─── train a subset of existing weights: BitFit / BEFT (biases), LN-tuning, top layers
                      ├─ REPARAMETERISED ─ ΔW in a structured low-dim form: LoRA, DoRA, PiSSA, VeRA, AdaLoRA, LoHa/LoKr,
                      │                     OFT/BOFT (orthogonal rotations), HiRA (Hadamard high-rank)
                      └─ HYBRID ────── combinations (e.g. adapters + prefixes; MAM, UniPELT)
Method What is trained Update form Mergeable (zero latency)? Served by vLLM? Notes
LoRA $A\in\mathbb{R}^{r\times d_{in}}, B\in\mathbb{R}^{d_{out}\times r}$ per target linear $W_0 + \tfrac{\alpha}{r}BA$ Yes Yes (multi-LoRA) Default. Details in 09.03
DoRA LoRA plus a per-column magnitude $m,\frac{W_0+BA}{\lVert W_0+BA\rVert_c}$ Yes (after merge) Merge first Often slightly better at low rank; slower to train
(IA)³ Vectors $l_k, l_v, l_{ff}$ $k\odot l_k,\ v\odot l_v,\ h_{ff}\odot l_{ff}$ Yes (fold into $W$) No (merge first) Tiny (≈0.01%); good for few-shot, weaker on hard tasks
Bottleneck adapter $W_{down}\in\mathbb{R}^{m\times d}, W_{up}\in\mathbb{R}^{d\times m}$ $h + W_{up},\sigma(W_{down}h)$ No (nonlinear) No Adds sequential latency per layer
Prompt tuning $n$ virtual token embeddings input $[P; X]$ No No Competitive only for very large models; uses context
Prefix tuning / P-tuning v2 Per-layer virtual K, V attention over $[P_K; K], [P_V; V]$ No No Better than prompt tuning at small scale; uses KV cache
BitFit / BEFT Biases only $b + \Delta b$ Yes Merge first Many modern LLMs (Llama, Qwen) have no linear biases, which limits its use
VeRA Scaling vectors on shared frozen random $A, B$ $\Lambda_b B \Lambda_d A$ Yes Merge first 10× fewer parameters than LoRA
OFT / BOFT Orthogonal $R$ (block-diagonal / butterfly) $R,W_0$ Yes Merge first Preserves pairwise angles (hyperspherical energy)

Mergeability decides the serving story. A method whose update folds into $W$ runs at base-model speed after merging. A method that stays separate needs engine support (only LoRA is widely supported) or adds latency (adapters, soft prompts, which also consume context and KV-cache slots).

# 3. Counting Trainable Parameters (and Checking the Formulas)

For a Llama-style decoder with $L$ layers, hidden size $d$, MLP size $d_{ff}$, and GQA with $n_{kv}$ KV heads of dimension $d_h$:

$$ \begin{aligned} |\phi_{\text{LoRA}}| &= L \sum_{\text{targets}} r,(d_{in}+d_{out}),\ |\phi_{\text{(IA)}^3}| &= L,(2,n_{kv} d_h + d_{ff}),\ |\phi_{\text{prompt}}| &= n,d,\qquad |\phi_{\text{prefix}}| = L \cdot 2 \cdot n \cdot n_{kv} d_h . \end{aligned} $$

The code checks these closed forms against PEFT's own counts on a small Llama, then applies them to Llama-3-8B shapes.

python 
import torch
from transformers import LlamaConfig, LlamaForCausalLM
from peft import LoraConfig, IA3Config, PromptTuningConfig, PrefixTuningConfig, get_peft_model

def llama_linear_shapes(d, d_ff, n_heads, n_kv):
    hd = d // n_heads
    return {"q_proj": (d, d), "k_proj": (d, n_kv * hd), "v_proj": (d, n_kv * hd), "o_proj": (d, d),
            "gate_proj": (d, d_ff), "up_proj": (d, d_ff), "down_proj": (d_ff, d)}      # (in, out)

def peft_trainable(method, L, d, d_ff, n_heads, n_kv, r=16, targets=None, n_virtual=20):
    """Closed-form trainable-parameter counts for a Llama-style decoder with L layers."""
    shapes = llama_linear_shapes(d, d_ff, n_heads, n_kv)
    if method == "lora":
        return L * sum(r * (i + o) for k, (i, o) in shapes.items() if k in targets)
    if method == "ia3":          # scaling vectors on k, v outputs and on the MLP activation (down_proj input)
        return L * (shapes["k_proj"][1] + shapes["v_proj"][1] + d_ff)
    if method == "prompt":
        return n_virtual * d
    if method == "prefix":       # per layer: virtual keys and values
        return L * 2 * n_virtual * n_kv * (d // n_heads)
    raise ValueError(method)

ATTN = {"q_proj", "k_proj", "v_proj", "o_proj"}
ALL = ATTN | {"gate_proj", "up_proj", "down_proj"}
cfg = dict(L=4, d=256, d_ff=688, n_heads=8, n_kv=2)
tiny = LlamaConfig(vocab_size=1000, hidden_size=cfg["d"], intermediate_size=cfg["d_ff"], num_hidden_layers=cfg["L"],
                   num_attention_heads=cfg["n_heads"], num_key_value_heads=cfg["n_kv"])

def count(pcfg):
    torch.manual_seed(0)
    return get_peft_model(LlamaForCausalLM(tiny), pcfg).get_nb_trainable_parameters()[0]

checks = {
    "lora attn r16": (count(LoraConfig(r=16, target_modules=sorted(ATTN), task_type="CAUSAL_LM")),
                      peft_trainable("lora", **cfg, r=16, targets=ATTN)),
    "lora all r16": (count(LoraConfig(r=16, target_modules="all-linear", task_type="CAUSAL_LM")),
                     peft_trainable("lora", **cfg, r=16, targets=ALL)),
    "ia3": (count(IA3Config(target_modules=["k_proj", "v_proj", "down_proj"], feedforward_modules=["down_proj"],
                            task_type="CAUSAL_LM")), peft_trainable("ia3", **cfg)),
    "prompt 20": (count(PromptTuningConfig(num_virtual_tokens=20, task_type="CAUSAL_LM")),
                  peft_trainable("prompt", **cfg, n_virtual=20)),
    "prefix 20": (count(PrefixTuningConfig(num_virtual_tokens=20, task_type="CAUSAL_LM")),
                  peft_trainable("prefix", **cfg, n_virtual=20)),
}
for k, (lib, formula) in checks.items():
    print(f"{k:14s} peft={lib:8d} formula={formula:8d}")
    assert lib == formula, k

L8 = dict(L=32, d=4096, d_ff=14336, n_heads=32, n_kv=8)           # Llama-3-8B shapes (8.03B params)
for name, n in [("LoRA r=16 attn", peft_trainable("lora", **L8, r=16, targets=ATTN)),
                ("LoRA r=16 all-linear", peft_trainable("lora", **L8, r=16, targets=ALL)),
                ("LoRA r=64 all-linear", peft_trainable("lora", **L8, r=64, targets=ALL)),
                ("(IA)3", peft_trainable("ia3", **L8)),
                ("Prompt tuning (20 tok)", peft_trainable("prompt", **L8)),
                ("Prefix tuning (20 tok)", peft_trainable("prefix", **L8))]:
    print(f"8B {name:24s} {n / 1e6:8.3f} M  ({100 * n / 8.03e9:.4f}% of base, {n * 2 / 2**20:6.1f} MiB bf16)")

All five formulas match PEFT exactly. For Llama-3-8B:

Method Trainable % of base Adapter size (BF16)
LoRA r=16, attention only 13.6 M 0.17% 26 MiB
LoRA r=16, all linear 41.9 M 0.52% 80 MiB
LoRA r=64, all linear 167.8 M 2.09% 320 MiB

Most of the LoRA budget sits in the MLP: gate, up, and down hold 67% of all-linear r=16 parameters. That is also where the evidence says LoRA should go (09.03 §3).

# 4. What Each Family Can Express: a Controlled Experiment

Parameter count is not capacity. Where the parameters sit, and what function class the update spans, matters more. The experiment below does the following:

  1. "Pre-trains" a small network on a teacher task.
  2. Adapts it to a downstream task whose true change is low-rank weight updates plus bias shifts, the regime PEFT assumes.
  3. Compares methods at equal steps.
python 
import copy
import torch, torch.nn as nn

torch.set_num_threads(1); torch.manual_seed(0)
D_IN, H, D_OUT, N = 32, 128, 8, 2048

def mlp():
    return nn.Sequential(nn.Linear(D_IN, H), nn.GELU(), nn.Linear(H, H), nn.GELU(), nn.Linear(H, D_OUT))

def fit(model, X, Y, params, steps=800, lr=3e-3):
    opt = torch.optim.Adam(params, lr=lr)
    for _ in range(steps):
        loss = ((model(X) - Y) ** 2).mean()
        opt.zero_grad(); loss.backward(); opt.step()
    return float(loss.detach())

teacher_a = mlp()                                                      # "pre-training" task
X, Xte = torch.randn(N, D_IN), torch.randn(N, D_IN)
with torch.no_grad(): Ya = teacher_a(X)
base = mlp(); fit(base, X, Ya, base.parameters(), steps=1500)

teacher_b = copy.deepcopy(teacher_a)                                   # downstream: rank-2 change per layer + bias shift
with torch.no_grad():
    for m in teacher_b:
        if isinstance(m, nn.Linear):
            o, i = m.weight.shape
            m.weight += 0.6 * torch.randn(o, 2) @ torch.randn(2, i) / i ** 0.5
            m.bias += 0.1 * torch.randn(o)
    Yb, Yb_te = teacher_b(X), teacher_b(Xte)

class LoRALinear(nn.Module):
    def __init__(self, lin, r, alpha=None):
        super().__init__()
        self.lin, self.s = lin, (alpha or r) / r
        self.A = nn.Parameter(torch.randn(r, lin.in_features) / lin.in_features ** 0.5)
        self.B = nn.Parameter(torch.zeros(lin.out_features, r))       # B = 0: training starts exactly at the base
    def forward(self, x):
        return self.lin(x) + self.s * (x @ self.A.T) @ self.B.T

class IA3(nn.Module):                                                   # learned per-unit rescaling
    def __init__(self, n):
        super().__init__(); self.l = nn.Parameter(torch.ones(n))
    def forward(self, x): return x * self.l

class Adapter(nn.Module):                                               # Houlsby-style residual bottleneck
    def __init__(self, n, m=8):
        super().__init__(); self.down, self.up = nn.Linear(n, m), nn.Linear(m, n)
        nn.init.zeros_(self.up.weight); nn.init.zeros_(self.up.bias)
    def forward(self, x): return x + self.up(torch.relu(self.down(x)))

def variant(kind):
    m = copy.deepcopy(base)
    for p in m.parameters(): p.requires_grad_(False)
    if kind == "full":
        for p in m.parameters(): p.requires_grad_(True)
    elif kind == "head-only":
        for p in m[4].parameters(): p.requires_grad_(True)
    elif kind == "bitfit":
        for mod in m:
            if isinstance(mod, nn.Linear): mod.bias.requires_grad_(True)
    elif kind == "ia3":
        m = nn.Sequential(m[0], m[1], IA3(H), m[2], m[3], IA3(H), m[4])
    elif kind == "adapter":
        m = nn.Sequential(m[0], m[1], Adapter(H), m[2], m[3], Adapter(H), m[4])
    elif kind.startswith("lora"):
        m = nn.Sequential(*[LoRALinear(x, int(kind.split("-r")[1])) if isinstance(x, nn.Linear) else x for x in m])
    return m

with torch.no_grad():
    zero_shot = float(((base(Xte) - Yb_te) ** 2).mean())
res = {}
for kind in ("head-only", "bitfit", "ia3", "adapter", "lora-r2", "lora-r8", "full"):
    torch.manual_seed(1)
    m = variant(kind)
    params = [p for p in m.parameters() if p.requires_grad]
    fit(m, X, Yb, params)
    with torch.no_grad():
        res[kind] = (sum(p.numel() for p in params), float(((m(Xte) - Yb_te) ** 2).mean()) / zero_shot)
    print(f"{kind:10s} trainable={res[kind][0]:6d}  test MSE vs no-adaptation={res[kind][1]:.3f}")
total = sum(p.numel() for p in base.parameters())
assert res["lora-r2"][1] < res["bitfit"][1] and res["lora-r2"][0] < 0.1 * total
assert res["full"][1] < 0.5 and res["head-only"][1] > res["lora-r8"][1]
Method Trainable (of 21,768) Test MSE vs no adaptation
BitFit 264 (1.2%) 0.54
(IA)³ 256 (1.2%) 0.48
Head only (linear probe) 1,032 (4.7%) 0.28
Bottleneck adapter (m=8) 4,368 (20%) 0.11
LoRA r=2 1,104 (5.1%) 0.073
LoRA r=8 4,416 (20%) 0.037
Full FT 21,768 (100%) 0.030

Reading the results:

  • LoRA r=2 beats the bottleneck adapter with 4× fewer parameters, because its function class (low-rank $\Delta W$ in every layer) matches the true change.
  • Scaling-only methods ((IA)³, BitFit) can't rotate the representation, so they plateau.
  • The head-only probe can't fix earlier layers.

The general lesson holds beyond toys: choose the method whose update geometry matches the adaptation you need. LLM task adaptation is empirically low-rank-friendly (Aghajanyan et al., intrinsic dimension), which is why LoRA dominates.

# 5. Soft Prompts and Prefixes: When They Still Make Sense

For prompt tuning, the input becomes $[P; E(x)]$ with $P \in \mathbb{R}^{n\times d}$ learned. For prefix tuning, every layer's attention sees learned $P_K^{(\ell)}, P_V^{(\ell)}$:

$$ \mathrm{Attn}\big(Q,, [P_K; K],, [P_V; V]\big) = \lambda,\mathrm{Attn}(Q, P_K, P_V) + (1-\lambda),\mathrm{Attn}(Q, K, V), $$

where $\lambda$ is the softmax mass assigned to the prefix. A prefix therefore acts as a gated additive bias on attention outputs, a restricted update. This explains why prefix tuning trails LoRA on complex tasks (He et al., Towards a Unified View of Parameter-Efficient Transfer Learning).

Production verdict. Soft prompts consume context and KV cache, have no support in mainstream serving engines, are sensitive to initialisation and learning rate, and only match full fine-tuning at very large model scales (Lester et al.). Use them for research, for per-user personalisation vectors at huge tenant counts, or when you truly cannot touch the weights. Otherwise use LoRA.

# 6. Operating Adapters with PEFT

The core lifecycle is:

  1. train an adapter per task;
  2. save adapter weights only;
  3. load several onto one base;
  4. switch, combine, or merge for deployment.

The block below is tested on a small local model; with the real base, only the id changes.

python 
import os, tempfile, torch
from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model

BASE_ID = "meta-llama/Llama-3.1-8B-Instruct"                    # any causal LM; pin the revision
torch.manual_seed(0)
base = AutoModelForCausalLM.from_pretrained(BASE_ID, dtype=torch.float32)
cfg = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, target_modules="all-linear", task_type="CAUSAL_LM")
model = get_peft_model(base, cfg, adapter_name="summaries")
model.add_adapter("fiscal_notes", cfg)
model.print_trainable_parameters()
model.eval()                                                     # disable LoRA dropout for comparisons

with torch.no_grad():                                            # stand-in for training: perturb the B matrices
    for n, p in model.named_parameters():
        if "lora_B" in n:
            p.normal_(0, 0.02)

x = torch.randint(0, model.config.vocab_size, (1, 16))
outs = {}
for name in ("summaries", "fiscal_notes"):
    model.set_adapter(name)
    with torch.no_grad():
        outs[name] = model(x).logits
with model.disable_adapter(), torch.no_grad():
    outs["base"] = model(x).logits
print({k: round(float((v - outs["base"]).abs().max()), 4) for k, v in outs.items()})
assert not torch.allclose(outs["summaries"], outs["fiscal_notes"])

d = tempfile.mkdtemp()
model.save_pretrained(d)                                         # adapters only: one subfolder per extra adapter
sizes = {r: sum(os.path.getsize(os.path.join(r, f)) for f in fs) for r, _, fs in os.walk(d) if fs}
print({os.path.relpath(k, d): f"{v / 1024:.0f} KiB" for k, v in sizes.items()})

model.set_adapter("summaries")
merged = model.merge_and_unload(adapter_names=["summaries"])     # fold W0 + (alpha/r) B A into the base weights
with torch.no_grad():
    diff = float((merged(x).logits - outs["summaries"]).abs().max())
print("merged vs adapter max |diff|:", diff)
assert diff < 1e-4

Things to know:

  • model.eval() before any parity check. LoRA dropout is active in train mode and makes merged-vs-unmerged comparisons fail spuriously.
  • Merge in the serving precision. Merging into a BF16 base rounds $W_0 + \Delta W$ to BF16. Merging into a quantized base needs dequantize → merge → requantize (09.03 §5), with an eval after it.
  • Combining adapters. add_weighted_adapter (linear, SVD, TIES, DARE) can blend task adapters. Treat the result as a new model and evaluate it; blends interfere unpredictably.
  • Adapter metadata travels with the adapter: base model id and revision, PEFT version, target modules, rank, training data hash, eval report. Put it in the bundle manifest (08.05 §2), because an adapter on the wrong base is silently wrong.

# 6.1 Serving many adapters

             ┌───────────────── vLLM (one base model resident in GPU memory) ─────────────────┐
 requests ──►│ scheduler batches requests for DIFFERENT adapters together                     │
 model=      │   y = x W0  +  Σ_i  mask_i · s_i · (x A_i) B_i        (SGMV/Punica-style kernels) │
 "fiscal"    │ adapter cache: --max-loras (GPU slots) · --max-cpu-loras (CPU LRU) · --max-lora-rank │
 "summaries" └──────────────────────────────────────────────────────────────────────────────────┘
  • Multi-LoRA batching. One base forward pass is shared, and each request adds its own low-rank term. The overhead is typically a small percentage at moderate adapter counts (S-LoRA, Punica). Set --max-lora-rank to the largest rank you serve, because it sizes the buffers.
  • When to merge instead. Merge when there is one dominant adapter carrying most of the traffic, when you need maximum throughput, or when the method isn't LoRA. Serve the merged weights as a separate deployment.
  • Adapter registry. Store adapters in object storage keyed by (base digest, adapter name, version). Load them dynamically (vLLM supports runtime LoRA loading through its API when enabled). Route with the gateway: model="bill-assistant:fiscal_notes@v3" (08.01 §5).
  • Isolation. Treat an adapter like code: an adapter file is an executable behaviour change. Keep provenance and signatures, and only load from the registry (07.02 §2). A malicious adapter can implant backdoors.

# 7. Choosing a PEFT Method

Situation Choose Why
Default for LLM task adaptation LoRA, all linear layers, r=16–64 Mergeable, served natively, strong quality
GPU memory is the binding constraint QLoRA (09.03) 4-bit frozen base
Many tenants, tiny per-tenant data LoRA r=4–8 or VeRA/(IA)³ (then merge per tenant or keep LoRA for multi-serve) Adapter size and count
Need maximum quality at low rank DoRA, PiSSA init, rsLoRA (09.03) Better optimisation at small r
Must not change weights at all (vendor-hosted base) Prompt tuning / prefix (if supported) or plain prompting Only input-side control
Classification head on an encoder LoRA + trained head (modules_to_save) Head must be trained fully
Large dataset, big domain shift (new language, code-heavy) Full fine-tuning or high-rank LoRA LoRA capacity becomes limiting (09.03 §3)

# 8. Production Challenges and Solutions

Target modules missed Weak adaptation despite high rank target_modules="all-linear"; print trainable params per module type

Engine doesn't support the method Can't deploy Merge into the base; or stay within LoRA for multi-adapter serving

Supply-chain risk Unknown adapters from the hub Signed adapters, a SafeTensors-only policy, scanning (07.02 §2)

# 9. Hands-On Projects

# Project 1 — PEFT Method Bake-Off on a Legislative Task

User stories

  • As the ML lead, I want evidence-based defaults for which PEFT method and rank to use on our tasks, not blog-post folklore.

Acceptance criteria

  • Task: amendment explanation, where the input is bill text with strike/insert markup and the output is a plain-language explanation. Use 3,000 training and 500 test examples, split by session.
  • Methods: LoRA (attention-only vs all-linear; r ∈ {8, 32, 128}), DoRA r=32, (IA)³, prefix tuning, and full FT as the reference. Seeds fixed and three runs each.
  • The report gives, per method: trainable parameters, peak GPU memory, wall-clock time, test score with 95% CI, adapter size, and mergeability and serving support.
  • A recommendation memo sets the default config per task class, backed by the data. The closed-form parameter counts match PEFT's for every configuration.

Step-by-step

  1. Build the dataset (09.01 §4 hygiene), including chat templates and masking.
  2. Write one training script parameterised by a PEFT config. Log memory with torch.cuda.max_memory_allocated.
  3. Run the grid, then evaluate with the 06.01 harness and a paired bootstrap against the full-FT reference.
  4. Plot quality vs trainable parameters and vs memory, and mark the Pareto front.
  5. Write the memo and turn the chosen configs into templates.

# Project 2 — Multi-Adapter Serving for Department Tasks

User stories

  • As the platform owner, I want one GPU deployment to serve summaries, fiscal-note drafting, committee-minutes cleanup, and constituent-letter triage adapters, with per-adapter versioning and rollback.

Acceptance criteria

  • vLLM serves ≥ 4 LoRA adapters over one base, loaded from an adapter registry (object storage plus a metadata DB). The gateway routes model="<app>:<adapter>@<version>".
  • A load test with a mixed-adapter traffic ratio holds TTFT and ITL within 10% of single-adapter serving at the same QPS. The report covers --max-loras and --max-lora-rank choices.
  • Rolling back one adapter version affects only that adapter's traffic and is visible in traces (bundle digest per adapter).
  • Loading an adapter whose base digest doesn't match the deployed base is rejected.

Step-by-step

  1. Train or obtain four adapters, all with metadata files.
  2. Configure vLLM with --enable-lora and dynamic loading. Build a registry sidecar that validates the base digest before loading.
  3. Extend the 08.01 gateway to parse adapter routes and stamp traces.
  4. Run the load test (08.03 harness) across adapter mixes and tune the slots.
  5. Game day: roll back one adapter under load.

# Project 3 — PEFT from Scratch: LoRA, (IA)³, and Prefix Tuning on a Real Decoder

User stories

  • As an ML engineer, I want to implement the three core families myself, so I can debug library behaviour and evaluate new methods quickly.

Acceptance criteria

  • Pure-PyTorch implementations inject LoRA (into nn.Linear), (IA)³ (hooks on k/v/MLP activation), and prefix tuning (past-key-values injection) into a small open decoder (≤ 1.5B).
  • Trainable-parameter counts match PEFT exactly, and outputs match PEFT's for the same weights to within 1e-5.
  • After fine-tuning on a small task, each implementation reaches within 1 point of the PEFT-library result.
  • A written analysis relates the §5 prefix-attention decomposition to measured behaviour. For example, measure the prefix attention mass $\lambda$ per layer after training.

Step-by-step

  1. Write module-replacement utilities (walk named_modules, wrap targets).
  2. Implement the three methods, then copy PEFT's initialisation for parity tests.
  3. Train with a shared loop and compare with PEFT.
  4. Instrument the attention to log $\lambda$ per layer and head for prefix tuning.
  5. Write up the results.
